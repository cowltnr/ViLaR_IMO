### 보충 설명

#### I2ICF 확장 방향

- `[확정]` 연구 방향을 LIMO 1대의 단방향 정보 전송에서 여러 차량·로봇이 정보를 주고받는 양방향 구조로 확장한다.
- `[제안]` 각 이동체는 정적 지도 전체를 반복 전송하지 않고, 로컬에 Static Layer(정적 레이어)를 유지한다.
- `[제안]` Edge Server에는 Dynamic Obstacle/Object Update(동적 장애물·객체 갱신)만 선택적으로 전송한다.
- `[제안]` 전송 방식은 Pub/Sub(발행·구독)와 Push(서버로 직접 전송)를 비교한다. 방식 선택은 데이터 지연, 대역폭, 누락 복구, 구현 복잡도를 실험한 뒤 결정한다.

#### 시스템 구조 및 Architecture

- `[확정]` Sensor 입력부터 SLAM, 경로 생성·선택, 제어, 정보 공유까지 이어지는 전체 Robot Motion Control Pipeline(로봇 모션 제어 파이프라인) 그림이 필요하다.
- `[제안]` 비교·검토할 후보 요소로 SLAM, VLA(Vision-Language-Action), Diffusion Model(확산 모델)을 Architecture에 배치한다. 현재 구현 기능으로 표현하지 않는다.
- `[제안]` 로봇별 Worker Agent(작업 수행 에이전트)와 상위 Manager Agent(작업 조정 에이전트)를 분리하고, MCP(Model Context Protocol)와 A2A(Agent-to-Agent) 통신 연계를 검토한다.

- 확인 필요: 2026-08-19 회의에서 Manager Agent/MCP/A2A를 이번 연구의 필수 구현 범위로 둘지, 장기 후보로 둘지 결정한다.

- 현재 Route는 `waypoint_tools/waypoint_routes/routes.py`의 `wp1`~`wp5`로 사전 정의되어 있다. SLAM 기반 실시간 Path Candidate 생성은 아직 구현되지 않았다.

- 따라서 양방향 정보 공유, Static/Dynamic Layer 분리, MCP/A2A, VLA, Diffusion Model은 구현 완료가 아니라 연구·설계 후보로 기록한다.

## 4. 종합 정리

### 이번 주 결론

- `[확정]` 연구의 다중 이동체 확장 목표는 환경정보의 양방향 공유이다.

- `[확정]` 다음 구현 전에 현재 Pipeline과 후보 확장을 한눈에 구분하는 전체 Architecture가 필요하다.
- `[제안]` Worker/Manager Agent와 MCP/A2A는 I2ICF와 분리된 Architecture 후보로 검토한다.
- `[확정]` 해외 유사 연구 Survey를 통해 비교 기준과 차별화 근거를 확보한다.

### 연구 방향에 미치는 영향

- 단일 이동체의 VLM Route 선택 연구에서, `SLAM 기반 Path 생성 + VLM 후보 선택 + 다중 이동체 환경정보 공유`로 연구 범위가 확장된다.
- 기존 `wp1`~`wp5`와 Point Follower/Pure Pursuit는 재현 가능한 Baseline으로 보존한다.
- 새 방식은 별도 Candidate로 추가하고 동일 조건에서 안전성, 경로 품질, 지연, 통신량을 비교한다.
- Agent Architecture는 다중 이동체 공유 효과와 혼합 평가하지 않고 독립된 질문과 지표를 정의한 후 채택 여부를 결정한다.
