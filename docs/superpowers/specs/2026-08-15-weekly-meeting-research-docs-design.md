# 주간 회의 및 연구 방향 문서 관리 설계

## 목적

매주 회의가 끝난 뒤 사용자가 수동으로 업데이트를 요청하면, 저장소에 있는 회의록과 대화에서 전달된 보충 내용을 출처별로 분리해 기록하고 이를 종합해 현재 연구 방향을 갱신한다.

## 실행 방식

- 자동 예약 작업을 사용하지 않는다.
- 사용자가 회의록 파일을 저장하고 대화에서 보충 내용을 전달한 뒤 `이번 주 회의 문서 업데이트`라고 요청하면 실행한다.
- 해당 요청이 없는 상태에서는 기존 회의 문서와 연구 방향 문서를 자동으로 변경하지 않는다.
- Live ROS2, Isaac Sim, Ollama, Flask, 실제 LIMO는 실행하지 않는다.

## 파일 구조

```text
docs/
├── meetings/
│   ├── index.md
│   └── YYYY-MM-DD.md
└── research-direction.md
```

### `docs/meetings/index.md`

회의 문서의 날짜, 제목, 입력 회의록, 상태를 연결하는 목록이다.

상태는 다음 중 하나를 사용한다.

- `정리 완료`: 회의록과 전달된 대화 내용이 종합됨
- `보충 대기`: 회의록은 있으나 대화 기반 보충 내용이 아직 없음
- `확인 필요`: 출처 간 충돌이나 결정되지 않은 내용이 있음

### `docs/meetings/YYYY-MM-DD.md`

회의일 기준으로 한 파일을 만들며 다음 구조를 고정한다.

```markdown
# YYYY-MM-DD 주간 회의

## 입력 출처

## 1. 회의록 기반

### 논의 내용
### 결정 사항
### Action Items
### 미해결 질문

## 2. 대화 기반

### 보충 설명
### 정정 사항
### 추가 요청

## 3. 출처 간 차이와 해결

## 4. 종합 정리

### 이번 주 결론
### 연구 방향에 미치는 영향
### 다음 실행 항목
### 보류·위험 요소
```

`회의록 기반`에는 PDF, TXT, MD 등 저장된 회의 자료에서 직접 확인한 내용만 작성한다. PDF를 근거로 할 때는 확인 가능한 경우 페이지 번호를 기록한다.

`대화 기반`에는 사용자가 현재 대화에서 추가하거나 정정한 내용만 작성한다. 대화 내용이 기존 회의록을 수정하는 경우 기존 문장을 삭제하지 않고 정정 사항으로 남긴다.

`종합 정리`에는 두 출처를 결합한 현재 결론을 기록한다. 제안된 아이디어를 확정 결정처럼 표현하지 않는다.

### `docs/research-direction.md`

매주 회의별 기록과 달리 현재 시점의 연구 방향을 보여주는 누적 문서다.

```markdown
# SDV Robocar 연구 방향

## 현재 연구 목표
## 확인된 시스템 Baseline

## 연구 축
### SLAM·Path Planning
### VLM 활용 시나리오
### 다중 이동체 환경정보 공유

## 실행 순서
### Now
### Next
### Later

## 평가 기준
## 미해결 질문과 위험
## 결정 이력
```

`Now`에는 바로 다음 실험 주기에 수행할 항목만 둔다. `Next`에는 Now가 검증된 뒤 진행할 항목을, `Later`에는 장기 확장 후보를 둔다.

## 출처 및 판단 규칙

### 출처 분리

- 회의록에서 확인된 사실과 대화에서 추가된 설명을 같은 문단에 섞지 않는다.
- 종합 결론에는 관련 회의 문서의 상대 경로를 근거로 연결한다.
- 코드의 현재 동작을 설명할 때는 관련 production code와 test를 확인한다.
- 문서와 코드가 다르면 코드를 현재 동작으로 취급하고 불일치를 기록한다.

### 충돌 처리

- 회의록과 대화 내용이 다르면 양쪽 내용을 모두 `출처 간 차이와 해결`에 기록한다.
- 사용자가 대화에서 명시적으로 정정한 경우 종합 결론에는 최신 정정을 반영한다.
- 정정 여부가 불명확하면 임의로 결론을 내리지 않고 `확인 필요`로 남긴다.

### 상태 구분

각 주요 항목에는 필요한 경우 다음 표시를 사용한다.

- `확정`: 회의에서 결정되었거나 사용자가 명시적으로 확정
- `제안`: 검토 대상으로 제시되었으나 아직 결정되지 않음
- `보류`: 선행 조건이나 추가 검증이 필요
- `폐기`: 더 이상 진행하지 않기로 결정

### 연구 방향 갱신

- 새 회의에서 변경된 내용만 누적 문서에 반영한다.
- 과거 결정은 삭제하지 않고 `결정 이력`에 상태 변경을 남긴다.
- Baseline 구현을 보존하고 새로운 방법은 별도 Candidate로 기록한다.
- 실험 결과가 없으면 성능 향상이나 완료를 주장하지 않는다.
- 실패, 중립 결과, 제외된 실험도 연구 판단에 영향을 주면 기록한다.

## 수동 업데이트 절차

1. 사용자가 회의록 PDF, TXT 또는 MD를 저장소에 저장한다.
2. 사용자가 대화에서 보충 설명과 정정 사항을 전달한다.
3. 사용자가 `이번 주 회의 문서 업데이트`라고 요청한다.
4. 관련 MD와 입력 회의록을 먼저 읽는다.
5. 관련 production code와 test를 확인해 현재 Baseline을 검증한다.
6. 해당 날짜의 `docs/meetings/YYYY-MM-DD.md`를 생성하거나 갱신한다.
7. `docs/meetings/index.md`에 회의와 상태를 추가한다.
8. 종합 결론을 근거로 `docs/research-direction.md`의 Now, Next, Later 및 결정 이력을 갱신한다.
9. 변경된 문서와 남은 확인 사항을 사용자에게 보고한다.

회의록은 현재 사용 중인 `Robot Motion Control Meeting/`에서 우선 찾고, 사용자가 다른 경로를 명시하면 해당 경로를 사용한다. 대화 기반 내용은 현재 대화에서 명시적으로 전달된 내용만 사용하며, 자동 실행이 과거 채팅 전체를 임의로 복원할 수 있다고 가정하지 않는다. 회의 문서의 날짜는 파일 생성일이 아니라 사용자가 확인한 실제 회의일을 사용한다.

## 완료 기준

- 회의록 기반 내용과 대화 기반 내용이 별도 절에 존재한다.
- 종합 정리에서 확정, 제안, 보류가 구분된다.
- 각 회의 문서가 입력 출처를 연결한다.
- 연구 방향 문서가 최신 회의 결론과 일치한다.
- 출처 간 충돌이 숨겨지지 않는다.
- 근거가 없는 구현 완료나 성능 개선을 주장하지 않는다.
- 기존 회의 문서와 실험 산출물을 삭제하거나 덮어쓰지 않는다.
