슬라이드 3. 왜 Predefined Route 선택 방식을 바꿔야 하는가?
시간: 1:00~2:10 / 약 1분 10초
============================================================

[대본]
현재 프로젝트에서는 routes.py에 wp1부터 wp5까지의 좌표가 수동으로 정의되어 있습니다. 사용자의 Goal이 들어오면 해당 Goal을 포함하는 Route만 Candidate로 만들고, VLM Server는 그 Candidate의 이름 중 하나를 선택합니다. 선택된 Route는 Point Follower 또는 Pure Pursuit가 추종합니다.

즉, 현재 VLM은 새로운 Path를 생성하는 것이 아닙니다. 이미 만들어진 wp1부터 wp5 사이에서 하나를 선택하는 역할만 합니다.

이 방식은 현재 시스템을 재현하고 비교하기 쉬운 Baseline이라는 장점이 있습니다. 하지만 장애물의 위치나 통로의 상태가 달라졌을 때, 그 상황에 맞는 새로운 Path 형상을 만들 수 없습니다. 새로운 Route가 필요할 때마다 사람이 좌표를 추가하거나 수정해야 하고, 현재 Map의 변화와 로봇의 Pose도 Candidate 생성에 직접 반영되지 않습니다.

따라서 기존 구현을 삭제하는 것이 아니라 비교 Baseline으로 보존하고, SLAM Map을 이용해 Dynamic Path를 생성하는 방식을 별도의 Candidate 방법으로 추가하는 것이 적절합니다.

[강조]
현재 방식은 “경로 생성”이 아니라 “사전 정의 Route 선택”이라는 점을 강조합니다.

[전환]
그렇다면 SLAM 기반 구조에서 실제 Path는 어느 모듈이, 어떤 순서로 생성하는지 설명하겠습니다.

슬라이드 4. 제안 구조 — SLAM은 Map, Planner는 Path
시간: 2:10~3:35 / 약 1분 25초
============================================================

[대본]
여기서 가장 먼저 구분해야 할 점은 SLAM이 직접 길을 만드는 것은 아니라는 점입니다.

Camera, 2D LiDAR, Odometry가 들어오면 SLAM Toolbox는 Map과 현재 Pose를 제공합니다. 이 정보에 정적 지도, 실시간 장애물, 차량의 Footprint, 그리고 필요한 경우 Semantic Cost를 결합해 Global Costmap을 구성합니다. 실제 Path Candidate는 그다음 단계의 Planner가 생성합니다.

첫 번째 연구 Baseline은 Nav2의 기본 Global Planner가 하나의 Path를 생성하고, 장애물이 나타나면 Replanning하는 방식으로 잡을 수 있습니다. 이후에는 K-Shortest Paths를 이용해 서로 다른 복수의 경로를 만들고, 차량의 회전 반경이 중요한 구간은 Hybrid-A*로 보정하는 방식을 Candidate로 비교합니다.

생성된 Path는 바로 VLM으로 보내지 않습니다. 먼저 Hard Filter에서 충돌 여부, 통로 폭, 곡률, 회전 반경처럼 수치로 검증 가능한 조건을 확인합니다. 이 단계를 통과한 Candidate만 VLM Selector에 전달합니다.

VLM은 사람 밀집도, 바닥 상태, 러그와 같은 Semantic 요소처럼 단순한 거리 Cost만으로 설명하기 어려운 상황에서 Candidate의 의미적 우선순위를 판단합니다. 마지막으로 Safety Validator가 다시 결과를 검증하고, 검증이 성공한 경우에만 Controller가 주행합니다.

정리하면 SLAM은 Map과 Pose를 제공하고, Planner가 Candidate를 생성하며, Hard Filter와 Safety Validator가 안전을 담당하고, VLM은 안전한 후보 안에서 의미 기반 선택만 수행합니다.

[전환]
이 구조가 실제 장애물 상황에서 어떻게 자동 우회로 이어지는지 순서대로 보겠습니다.

슬라이드 5. 장애물 발견 시 자동 우회는 어떻게 동작하는가?
시간: 3:35~5:00 / 약 1분 25초
============================================================

[대본]
주행 중 새로운 사람이나 장애물이 발견됐다고 가정하겠습니다.

첫 번째 단계는 감지입니다. Camera와 LiDAR 정보를 통해 기존 Path 위의 장애물을 확인합니다. 두 번째 단계에서는 Replanning보다 먼저 Local Safety가 로봇을 정지시킵니다. 즉, 새로운 Path를 계산하는 동안 기존 명령으로 계속 주행하지 않습니다.

세 번째로 감지된 장애물을 Costmap의 Obstacle Layer에 반영합니다. 사람이나 이동 물체와 같은 임시 장애물을 SLAM Map 자체에 영구적으로 기록하면, 장애물이 사라진 뒤에도 잘못된 정보가 남을 수 있습니다. 따라서 이런 정보는 timestamp와 TTL을 가진 임시 Obstacle로 관리하는 것이 적절합니다.

네 번째로 기존 Path가 새 장애물과 충돌하면 해당 Path를 무효화하고, 현재 Pose에서 Goal까지 K개의 Candidate를 다시 생성합니다. 그림에서는 직진 Path가 막혔기 때문에 위쪽 우회와 아래쪽 우회가 새로운 Candidate가 됩니다.

마지막으로 Hard Filter, VLM Selection, Safety Validation을 다시 수행합니다. 모든 검증을 통과한 경우에만 주행을 재개합니다. VLM 응답이 잘못됐거나 timeout이 발생한 경우에는 기존 Route를 임의로 선택하지 않고 정지 상태를 유지해야 합니다. 또한 /sim/cmd_vel을 발행하는 Controller는 항상 하나만 활성화해야 합니다.

[전환]
지금까지가 단일 이동체의 실시간 Path 생성입니다. 다음부터는 이 정보를 여러 이동체가 어떻게 공유할지 설명하겠습니다.

슬라이드 6. I2ICF 확장 — 관측을 다른 이동체의 Planning에 연결
시간: 5:00~6:35 / 약 1분 35초
============================================================

[대본]
이번 연구에서 I2ICF는 intent 해석이나 policy control을 구현하기 위한 개념으로 사용하지 않습니다. 여러 Mobile Object, 즉 여러 차량과 로봇이 수집한 환경정보를 공유한다는 측면으로만 범위를 제한합니다.

예를 들어 이동체 A인 LIMO가 Camera, LiDAR, Odometry를 통해 장애물을 발견하면, 이를 단순 이미지가 아니라 위치, 종류, 신뢰도, 관측 시간과 같은 환경 사건으로 변환해 Shared Environment DB로 Upload합니다.

Edge 또는 Cloud의 Information Aggregator는 여러 이동체가 보낸 장애물, Path, Terrain 정보를 시간과 출처 기준으로 통합합니다. 이후 이동체 B는 Shared Data Interface를 통해 자신에게 필요한 정보를 수신합니다.

여기서 중요한 점은 주행 제어 명령이나 완성된 조향 명령을 그대로 공유하지 않는다는 것입니다. 서로 다른 이동체는 차체 크기, 회전 반경, 구동 방식과 센서 성능이 다르기 때문입니다. 따라서 이동체 B는 공유된 환경정보를 자신의 Costmap에 반영하고, Capability Filter를 거친 뒤 자신에게 적합한 Candidate를 다시 생성해야 합니다. 최종 안전 판단 역시 각 이동체의 Local Safety가 담당합니다.

현재 k8s_server.py는 JSON과 이미지를 저장하는 기능은 있지만, 다른 이동체가 정보를 조회하고 배포받는 Interface까지 제공하지는 않습니다. 따라서 이 부분은 향후 Shared Environment Interface로 새롭게 설계해야 하는 제안 영역입니다.

[강조]
I2ICF 확장의 핵심은 “명령 공유”가 아니라 “환경정보 공유 후 각 이동체가 재판단”하는 것입니다.

[전환]
이 구조의 효과를 확인하기 위해 어떤 이기종 조합과 조건으로 실험할지 보겠습니다.

슬라이드 7. 이기종 실험 — 같은 정보, 다른 Path 판단
시간: 6:35~8:20 / 약 1분 45초
============================================================

[대본]
이기종 실험의 핵심 가설은 동일한 환경정보라도 이동체의 Capability에 따라 다른 Cost와 다른 Path 판단이 나와야 한다는 것입니다.

예를 들어 좁은 통로가 있을 때 차체 폭이 큰 LIMO는 통과할 수 없지만, 소형 차동 구동 로봇은 통과할 수 있습니다. 두꺼운 러그는 LIMO에 미끄럼 위험과 높은 Cost가 될 수 있지만, 다른 바퀴와 구동 방식을 가진 로봇에는 다른 Cost가 될 수 있습니다. UAV는 통과 여부를 판단하는 대신 상공에서 장애물 위치를 관측해 지상 로봇에 제공할 수 있습니다.

낮은 장애물처럼 2D LiDAR에 사각이 생길 수 있는 대상은 Depth Sensor나 다른 관측 플랫폼이 재확인할 수 있습니다. 임시 사람 정보는 TTL 동안만 유효하게 사용하고, 새로운 관측이 들어오면 위치와 시간을 갱신합니다.

정보 공유를 위해서는 공통 Shared Event Schema가 필요합니다. 최소 항목으로 source_mo_id, map_id, pose와 covariance, class, geometry, confidence, timestamp, TTL, evidence URI를 검토할 수 있습니다. 이후 위조 정보 검증이 필요하다면 signature도 추가합니다.

실험은 단계적으로 비교합니다. S0는 정보 공유가 없는 Baseline, S1은 Raw JSON 공유, S2는 TTL과 Confidence를 반영한 공유, S3는 이동체 Capability까지 반영한 공유입니다.

첫 실험에서는 모든 이동체가 동일한 Map 좌표계를 사용해 정보 공유 효과만 분리해서 측정하는 것이 좋습니다. 그다음 단계에서 독립 SLAM Map 간 Alignment 문제로 확장합니다.

Metrics는 Goal 도달률, Replan 횟수, 이동거리, 공유 지연, 만료된 정보로 인한 Stale Error, Capability Mismatch, 그리고 통신 장애 시 안전 상태 유지 여부를 사용합니다.

[전환]
마지막으로 이 연구를 실제로 어떤 순서로 진행할지 정리하겠습니다.

슬라이드 8. 단계별 Research Roadmap과 회의 결정사항
시간: 8:20~10:00 / 약 1분 40초
============================================================

[대본]
연구는 여섯 단계로 진행하는 것이 적절합니다.

0단계에서는 현재 Baseline을 재현하고 안전 결함을 먼저 정리합니다. 특히 VLM 실패 시의 동작과 중복 Publish 가능성을 수정하고, Offline Safety Test를 통해 정지 상태가 유지되는지 확인합니다.

1단계에서는 slam_toolbox와 Nav2를 이용해 단일 Path Replanning Baseline을 구축합니다. 2단계에서는 K-Shortest Paths와 Hybrid-A*를 이용해 복수 Candidate를 생성합니다. 3단계에서는 Hard Filter를 통과한 Candidate에만 VLM Semantic Selection을 적용하고, Safety Validator를 마지막에 배치합니다.

4단계에서 LIMO와 차동 구동 로봇을 이용한 이기종 정보 공유 실험을 진행합니다. 처음에는 공통 Map과 공통 Event Schema를 사용합니다. 5단계에서는 네트워크 지연, Packet Loss, 만료 정보, 위조 정보 상황에서도 안전하게 정지하거나 Local 정보로 전환할 수 있는지 검증합니다.

이번 회의에서 우선 결정할 사항은 다섯 가지입니다. 첫째, slam_toolbox와 Nav2를 1차 SLAM 및 Planner 조합으로 사용할지 여부입니다. 둘째, K-Shortest Paths와 Hybrid-A*를 우선 Candidate로 검증할지 여부입니다. 셋째, VLM의 역할을 Path 생성이 아니라 안전한 후보 사이의 Semantic Selection으로 제한할지 여부입니다. 넷째, 이기종 조합을 LIMO와 차동 구동 로봇으로 시작할지 여부입니다. 다섯째, 공유 범위를 Obstacle, Path, Terrain과 TTL, Confidence까지로 설정할지 여부입니다.

평가에서는 Route 완주율만 보지 않고 충돌과 주행 경계 위반, Planning Latency의 p95, 최소 장애물 여유 거리, Replan과 Stop 횟수, VLM timeout, 통신 장애 시 정지 유지 여부를 함께 기록해야 합니다.

검증 순서는 Offline Test, 기록 데이터 Replay, Isaac Sim, 실제 LIMO 순서로 진행합니다. Baseline과 Candidate는 동일한 Route, 시작점, Goal, 속도 제한, 반복 횟수와 Metrics를 사용해 비교해야 합니다.

정리하면, 현재의 Predefined Route 방식을 비교 가능한 Baseline으로 보존하면서 SLAM 기반 Dynamic Path 생성으로 확장하고, 이후 여러 이동체가 환경정보를 공유하되 각 이동체가 자신의 Capability에 맞게 다시 판단하는 구조를 검증하는 것이 이번 연구의 방향입니다.

이상으로 발표를 마치겠습니다. 감사합니다.

발표 직전 확인 사항
============================================================

1. “SLAM이 Path를 생성한다”가 아니라 “SLAM은 Map과 Pose를 제공하고 Planner가 Path를 생성한다”고 설명한다.
2. VLM은 Hard Filter를 통과한 안전한 Candidate 안에서 Semantic Selection만 수행한다고 설명한다.
3. VLM 오류 또는 timeout 시 정지를 유지한다고 설명한다.
4. I2ICF에서는 intent 해석과 policy control을 다루지 않는다고 명확히 말한다.
5. 이동체 간에는 주행 명령이 아니라 장애물·Path·Terrain 정보를 공유한다고 설명한다.
6. 현재 구현과 향후 제안 구조를 구분해서 말한다.
7. 실제 로봇 검증 전에 Offline Test와 Replay, Isaac Sim 검증을 먼저 수행한다고 설명한다.
